_Аннотация_

Для автоматизации управления нормативными документами, в частности для решения
задачи поиска противоречий, требуется формальный язык представления норм,
обладающей достаточно выразительной формальной моделью, системой модулей,
прослеживаемость к источнику, и пригодным для автоматизации создания программ на
языке. В работе проведён обзор решений в дизайне языка, удовлетворяющих данным
требованиям, на примере ранее представленного ранее формализма DDL-LTLF.

_Ключевые слова:_ требования, нормативные документы, промежуточное
представление, деонтическая логика, LTLf, DSL, трассируемость, поиск
противоречий.

# Введение

В рамках цифровой трансформации стандартизации
[@golovin-standards-digitalization] возникает задача автоматизированного поиска
противоречий внутри нормативных документов, между нормативными документами, а
также между нормативными документами и цифровыми моделями изделий (объектов
стандартизации). Процесс поиска противоречий не сводится к лексическому
сравнению фрагментов текста. Противоречие может возникать между обязанностью и
запретом, между общей нормой и исключением, между требованиями к разным
состояниям системы или между документами, использующими разные термины для одной
сущности. Поэтому система поиска противоречий должна работать не только с
текстом, но и с формальным представлением нормативного документа.

Существующие форматы обмена требованиями, например ReqIF, решают важную задачу
переносимости требований между инструментами, но не задают формальную семантику
требований [@omgReqIF12]. Следовательно, для поиска противоречий требуется
отдельное промежуточное представление: достаточно строгое для формальной
проверки и достаточно инженерное для построения, сопровождения и интеграции
моделей. В настоящей работе представлен язык MDL [@prokazin-mdl], являющийся
таким представлением на основе формализма DDL-LTLf [@prokazin2026ddl].
Рассмотрены требования к такому языку, и представлены основные решения,
реализующие требования.

# Требования к языку

MDL является DSL (доменно-специфичным языком), то есть ограничивается конкретной
предметной областью, и за счёт этого может эффективнее решать задачи
пользователей, чем универсальный язык программирования [@fowler2010dsl].
Предметная область MDL -- формальное представление требований из нормативных
документов, и анализ противоречий в множестве требований. Из этого следует
основные группы требований к языку.

Формальная семантика языка должна быть достаточно выразительной для формально
точного представления различных норм. Модель построенная на языке должна
выражать сами нормы, деонтические и временные отношения между нормами и
атрибутами модели.

Язык должен поддерживать композицию модулей. В первую очередь, сами противоречия
зачастую возникают не внутри одного нормативного документа (или эквивалентному
ему модуля MDL) а на пересечении нормативных документов. Во вторых, сами
требования из разных документов часто ссылаются на другие документы. В третьих,
зачастую нормативные документы используют идентичные модели и концепции (списки,
даты, URL, и т.п.), унификация которых существенно упрощает автоматический
анализ, а включение заранее всех таких моделей в спецификацию невозможно.

Код на языке должен быть связан с первоисточником. Это важно для поддержки
трассируемости к источнику, то есть для каждого параметра модели (атрибута,
правила, предиката) должно быть ясно откуда это требование появилось с
максимальной возможной точностью. Это особенно важно в контексте задачи поиска
противоречий, для того чтобы в результате анализа эксперт получил ссылки на
конкретные положения конкретных стандартов, между которыми возникло
противоречие.

Кроме того, язык должен быть пригоден для автоматизации построения кода. С одной
стороны, множество форматов _умных_ нормативных документов могут быть процедурно
транслированы для того чтобы поддержать интероперабельность между разными
форматами. С другой стороны, существующее множество нормативных документов на
естественном языке может быть автоматизированно транслировано в формальный язык
с использованием современных генеративных моделей [@horner2026llmddl]. При этом
в контексте генерации исходного кода возникают дополнительные требования к
устойчивости генерации: система языка должна представлять инструменты
канонизации синтаксиса, разумные ограничения выразительности, средства
статического анализа, и другие инструменты, позволяющие получать более
предсказуемые результаты генерации кода.

# Семантическая структура MDL

Модель требований MDL можно представить как иерархию с тремя уровнями: термовый,
темпоральный, и деонтический.

На уровне термов описываются структуры данных, значения и вычисления. На
термовом уровне описывается предметная область, без нормативной или темпоральной
семантики. Рассмотрим пример описания прямой трубы заданой длины и радиуса на
MDL.

```mdl
type Pipe = { length: rat, radius: rat }

func has_positive_geometry(p: Pipe) -> bool:
    p.length > 0 and p.radius > 0
```

Функция `has_positive_geometry` не является правилом: она только задаёт предикат
над объектом. Для использования модели предметной области в темпоральных и
временных отношениях пригодны только выражения, имеющие тип `bool`, что
соответствует атомарной пропозиции в формализме DDL-LTLf. Кроме того, важно
уточнить ограничение термового уровня: в языке не представлено никаких
инструментов для создания _побочных эффектов_, таких как чтение/запись данных из
файлов, другие виды ввода-вывода, создание переменных и т.п. В этом смысле все
вычисления на MDL являются _чистыми_.

На темпоральном уровне булевы выражения могут быть связаны темпоральными
операторами. Таким образом строятся выражения наподобие

```mdl
has_positive_geometry(pipe) always
```

Поддерживаются темпоральные операторы `always`, `eventually`, `next`, `until` и
подобные. Семантика темпоральных операторов полностью соответствует LTLf
[@degiacomo2013ltlf]. При этом темпоральные выражения имеют место только в
правилах, определяемых на деонтическом уровне:

```mdl
entity pipe: Pipe

rule O positive_gemetry: has_positive_geometry(pipe) always
```

На деонтическом уровне определяется _модель объекта_ как множество именованных и
типизированных `entity`, и деонтические правила, которые могут быть определены
только над объектами `entity`. Явное выделение `entity` важно для межмодельного
выравнивания, которое позволяет обнаруживать противоречие между совершенно
независимыми MDL модулями. Сами правила целиком следуют деонтической семантике
DDL-LTLf, позволя определять модальность $\{O,F,P\}$ соответствующие
обязательству.

Кроме того, на деонтическом уровне реализована дефизибельность
[@governatori2018practical]. Рассмотрим пример:

```mdl
rule O perform_work when scheduled: work_done eventually

strict rule F unsafe_mode: system_unsafe always

defeater rule F maintenance_exception when maintenance: work_done always

override maintenance_exception > perform_work
```

Здесь `when` задаёт применимость правила, `override` — отношение приоритета.
`strict`-правила применяются безусловно, то есть не могут быть побеждены
никакими другими правилами; `defeater` может блокировать нижестоящее правило, не
создавая собственного требования. Отдельно стоит упомянуть особенность
деонтических разрешений: в деонтических логиках разрешение может пониматься как
отсутствие запрета или как позитивная норма; это различие обсуждается в работах
по сильным и слабым разрешениям в дефизибельной логике
[@governatori2013permissions]. Поэтому MDL не скрывает политику интерпретации
$P$, а параметризует её на уровне алгоритмов решателя.

За счёт такой слоистой семантической структуры достигается формальная точность
при сохранении удобства моделирования и переиспользования исходного кода.

# Система типов и базовый синтаксис

Базовый синтаксис MDL вдохновлён языками семейства ML. Такое решение в первую
очередь связано с целью моделирования предметной области с учётом статической
типизации, полиморфизма, и безопасностью обработки структурированных данных
[@milner1978polymorphism; @milner1997sml]. От ML напрямую унаследованы концепции
модулей, алгебраических параметрических типов, сопоставление с образцом и чистые
функции. Строгая система типов ML поддерживает однозначную семантику кода на
MDL. На уровне языка определены примитивные типы `int`, `rat`, `string`, `bool`,
и возможность определять пользовательские типы-произведения и типы-суммы. В
отличие от других ML-подобных языков, такого примитива как `unit` не определено,
так как он обычно используется для представления операций с побочными эффектами
или вычислений без результата, что не имеет смысла в контексте задачи
нормативного моделирования.

Типы-произведения описывают объекты с множеством атрибутов

```mdl
type Pipe = { length: rat, radius: rat }

entity pipe: Pipe

rule O exact_size: pipe = Pipe { length = 10, radius = 1 }
```

Типы-суммы, в свою очередь, описывают _варианты_ объекта, например

```mdl
type Number = int | rat
```

Другие, типичные для языков программирования примитивы, в MDL определены не на
уровне языка а на уровне стандартной библиотеки. Например, список определён как
параметрический тип-сумма:

```mdl
module std.collections.list

type List<T> = Empty | Cons(T, List<T>)

func len<T>(l: List<T>) -> int:
    case l:
    | Empty: 0
    | Cons(head, tail): 1 + len(tail)
```

# Модули и межмодельное выравнивание

Интеропреабельность между документами является одной из центральных проблем MDL.
Разные документы могут описывать одну сущность разными способами, например
`pipe.length`, `tube.len`, `pipeline.segment_length`. Для разрешения
противоречий между такими (идентичными по сути но различными по наименованиям и
структуре) моделями, в системе предусмотрена операция `align`. Эта операция
принимает ряд mdl модулей, и возвращает новый alignment-модуль, например

```mdl
module alignment_pipe_tube

import "./pipe.mdl" as m1
import "./tube.mdl" as m2

# align kind=field score=0.800 matcher=builtin
rule O alignment_001: m1.pipe.length = m2.tube.length always
```

При наличии подобного модуля в контексте решателя могут быть обнаружены
противоречия между разными способами представить одну и ту же сущность. Сам
механизм выравнивания построен на алгоритме `bdikit:coma` [@do2002coma]. Важная
особенность подхода с применением дополнительно alignment-модуля заключается в
возможности для эксперта оценить результат поиска противоречий с учётом
выравнивания. Например, если решатель выполнил ложно-положительное срабатывание,
эксперт увидит в цепочке приведшей к неразрешимости конкретное правило из
alignment-модуля, и сможет его удалить или уточнить стандартными средствами MDL
(так как alignment-модуль является обычным MDL-модулем).

# Трассируемость

Под _трассируемостью_ понимается возможность определить первоисточник каждого
элемента, который попал в MDL-модель. Например, при обнаружении противоречия
эксперт сможет получить ссылки на конкретные положения исходных стандартов, а не
на конструкции языка MDL. Для достижения этого все верхнеуровневые конструкции
MDL могут быть аннотированны ссылкой на источник, например:

```
@ rfc2822
module email
# ...
@ 3.4.1. Addr-spec specification
rule O email_is_correct = email_is_correct(email) always
```

При анализе противоречий, решатель возвращает не факт "разрешимо" или
"неразрешимо", а уточнённую информацию. Для непротиворечивого набор правил,
решатель представляет нормативную трасу (в соответствии с семантикой DDL-LTLf),
а для противоречивого - полный граф несовместимых требований, с аннотациями.

# Канонический синтаксис и Python DSL

Модуль MDL может быть представлен в двух форматах: каноническом MDL синтаксисе и
Python DSL синтаксисе.

Пример эквивалентных MDL модулей:

```python
from mdl.builder import ModelBuilder, always, call, ref

m = ModelBuilder("email")
m.entity("email", "string")
m.rule("email_addr_spec_correct", "O", always(call("email_is_correct", ref("email"))))
```

```mdl
module email

entity email: string

rule O email_addr_spec_correct: email_is_correct(email) always
```

Необходимость поддержки Python синтаксиса связана с автоматической генерацией
MDL, как в процессе процедурного извлечения правил из других формальных языков
представления требований, так и при генерации MDL кода из текста стандартов на
естественном языке.

# Ограничения подхода

Основное ограничение представленного языка MDL состоит в необходимости
экспертного анализа. Без дополнительных данных качество межмодельного
выравнивания с использованием COMA-подобных алгоритмов, ограничено примерно 75%
точностью. Даже современные LLM-подходы к формализации норм сталкиваются с
проблемами устойчивого именования атомов, межфрагментных ссылок и согласования
интерпретаций [@horner2026llmddl].

# Заключение

В работе рассмотрены основные решения в дизайне языка MDL как промежуточного
представления норм для автоматизированного поиска противоречий в нормативных
документах. Показано, что такая задача требует не только формальной
выразительности, но и инженерных средств сопровождения моделей: модульности,
трассируемости к источнику, статической типизации, ограниченной выразительности
термового уровня и поддержки автоматического построения кода. Предложенная
слоистая структура языка — термовый, темпоральный и деонтический уровни —
позволяет связать практическое описание нормативных требований с формальной
семантикой DDL-LTLf.

Практическая значимость MDL состоит в том, что язык задаёт единый слой между
текстом нормативного документа, формальной моделью и решателем противоречий.
Модульная организация и представление результатов межмодельного выравнивания в
виде обычных MDL-модулей позволяют эксперту проверять не только найденные
противоречия, но и предпосылки их возникновения. Ограничением подхода остаётся
зависимость результата от качества исходной формализации и выравнивания моделей;
дальнейшая работа должна быть направлена на уточнение спецификации MDL, развитие
