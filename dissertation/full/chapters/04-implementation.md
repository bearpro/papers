# 3. Методы реализации системы

В предыдущей главе была задана математическая модель DDL-LTLf и показано, что
для конечного горизонта задача поиска противоречий сводится к проверке
разрешимости булевой формулы. В этой главе описывается инженерная реализация
этой модели: язык MDL, решатель, инструменты разработки, способ подключения
внешних данных, контур вывода моделей из естественного языка, индекс отношений
между модулями и схема оценки качества. MDL в данной архитектуре является
промежуточным представлением между исходным нормативным текстом, формальной
семантикой DDL-LTLf и решателем [@fowler2010dsl; @prokazin-mdl].

## 3.1. Язык промежуточного представления MDL

MDL является самостоятельным DSL для записи нормативных моделей. При этом он не
является языком программирования общего назначения. Он представляет, в
компактной и проверяемой форме, следующие объекты: предметные сущности, их
свойства, факты, нормы с деонтическими модальностями, условиями применимости,
исключениями, приоритетами и ссылками на источники.

Инструментальная цепочка MDL имеет следующий вид:

```{.plain}
source .mdl
  -> lexer/parser
  -> AST
  -> formatter / linter / runtime / aligner
  -> bounded Z3 solver
```

Важное следствие такой архитектуры состоит в разделении вероятностных и
формальных этапов. Генерация модели, подбор имён, сопоставление модулей и
подключение внешних данных могут выполняться эвристически. Однако заключение о
наличии или отсутствии противоречия должно получаться только после формальной
проверки MDL-модулей решателем.

### 3.1.1. Язык

MDL является ML-подобным языком с синтаксисом, чувствительным к отступам,
статической типизацией, модулями, чистыми функциями, алгебраическими типами
данных и сопоставлением с образцом. Использование этих конструкций связано с
двумя требованиями к формализации нормативных документов. Во-первых, модель
должна явно фиксировать предметную структуру документа: объекты, роли,
состояния, измеряемые величины и допустимые варианты. Во-вторых, модель должна
быть пригодна для повторного использования и межмодульного выравнивания, поэтому
важны устойчивые имена, типы и области видимости [@milner1978polymorphism;
@milner1997sml].

Каждый файл MDL является модулем. В начале файла указывается имя модуля, затем
могут следовать импорты, открытие пространств имён и объявления верхнего уровня:
типов, функций, сущностей, правил, и фактов.

```{.plain}
module standards.invoice

import "std/collections.mdl"
open std.collections

type Invoice = {
  issued: bool,
  paid: bool,
  closed: bool
}

entity invoice: Invoice
```

Типы задают статическую форму данных. Язык представляет примитивные типы `bool`,
`int`, `rat`, `decimal`, `string` и `unit`; с использованием которых строятся
сложные типы: записи, кортежи и размеченные объединения. Записи и кортежи
реализуют типы-произведения, а размеченные объединения - типы суммы, то есть
_варианты_ значений.

```{.plain}
type Material =
  | Steel(grade: string)
  | Aluminium(alloy: string)
  | Polymer(unit)

type Product = {
  material: Material,
  has_certificate: bool,
  mass_kg: rat
}
```

`entity` объявляет именованную сущность модели. В терминах решателя это внешний
символ, значение которого подбирается или ограничивается при проверке. Например,
в модели изделия можно объявить `entity product: Product`.

`func` используется для чистых вспомогательных вычислений. Функция не имеет
побочных эффектов и всегда возвращает значение, поэтому сложный предикат
требования можно вынести из правила и затем использовать в темпоральной формуле
в составе правила.

```{.plain}
func is_certified_product(p: Product) -> bool:
  p.has_certificate and p.mass_kg > 0

rule O r1: is_certified_product(product) always
```

Семантически язык разделён на три уровня. **Первый уровень** — чистые термовые
выражения: литералы, арифметика, булевы связки, записи, кортежи, функции, `let`,
`if` и `case`. Конструкции на этом уровне близки к привычным языка
программирования общего назначения, в том смысле что могут быть _выполнены_, при
этом они не имеют нормативной семантики, и должны быть сведены к выражениям с
типом bool для участия в темпоральных выражениях. **Второй уровень** —
темпоральные выражения LTLf над булевыми предикатами: `always`, `eventually`,
`next`, `now` и `until` [@de-giacomo-vardi-ltlf]. Темпоральные выражения
напрямую участвуют в правилах на **третьем уровне** - уровне деонтических правил
с модальностями `O`, `P` и `F`, условиями применимости, исключениями и
приоритетами.

```{.plain}
rule O pay_issued_invoice when invoice.issued:
  invoice.paid eventually

rule F close_unpaid_invoice when invoice.issued:
  (invoice.closed and not invoice.paid) now
```

Модальность `O` выражает обязанность, `F` — запрет, `P` — разрешение. Условие
`when` задаёт применимость правила. Если условие отсутствует, правило считается
безусловным. Сила правила определяет его поведение при конфликте: обычные
правила являются дефизибельными, `strict rule` не поражается более приоритетными
правилами, а `defeater rule` может блокировать другое правило, не порождая
собственного обязательства.

```{.plain}
rule O run_when_scheduled when scheduled:
  machine.running eventually

strict rule F unsafe_operation when machine.is_unsafe:
  machine.running now

defeater rule O maintenance_exception when maintenance_window:
  machine.running now

override maintenance_exception > run_when_scheduled
```

`override` задаёт порядок приоритета между правилами. Благодаря этому MDL
представляет не только прямые требования, но и нормативную структуру: общую
норму, специальное исключение и правило, определяющее, какая норма побеждает в
конфликте [@governatori2013permissions; @governatori2018practical].

Отдельную роль играют аннотации источника. Они начинаются с символа `@`,
привязываются к модулю, импорту, типу, сущности, факту, правилу или приоритету и
сохраняются в структурном представлении модели. В процессе вывода аннотация не
участвует напрямую, но обеспечивает трассируемость результата вывода к исходному
документу [@gotel1994traceability; @alkhammash2015traceable-eventb].

```{.plain}
@source: ГОСТ 32125-2013, п. 5.2.2
rule O material_has_certificate:
  product.has_certificate always
```

Если решатель обнаруживает противоречие, аннотации позволяют показать эксперту
не абстрактный набор внутренних переменных, а конкретные правила и пункты
документов, участвующие в конфликте.

### 3.1.2. Алгоритм решателя

Целевой режим работы MDL — проверка противоречивости с помощью `mdl solve`.
Команда принимает один или несколько MDL-модулей, разрешает их импорты,
подключает стандартную библиотеку, учитывает факты, правила и приоритеты, после
чего строит задачу для Z3 на конечном горизонте. Горизонт задаётся явно
параметром `--horizon K` или перебирается в диапазоне `1..N` при использовании
`--max-horizon N`.

Вход решателя состоит из ряда MDL модулей, и параметров решателя (в первую
очередь - размер горизонта). Модули можно классифицировать следующим образом:

1. **Нормативные модули** — файлы, содержащие типы, сущности и правила,
   извлечённые из стандартов, договоров, RFC или иных нормативных источников.
2. **Модули контекста** — задают общие словари, типы предметной области, правила
   выравнивания или внешние факты.
3. **Факты о проверяемой ситуации** — ограничения, полученные из тестового
   сценария, цифровой модели изделия или внешней информационной системы, не
   являющиеся частью нормативного контекста.

С точки зрения внутреннего представления, каждая `entity` разворачивается в
набор переменных для каждого шага трассы. Факты становятся ограничениями на
допустимые значения этих переменных. Темпоральные выражения разворачиваются в
булевы формулы над конечным горизонтом. Для правил дополнительно учитываются
условия применимости, модальность, сила правила и отношение приоритета. После
этого решатель (Z3) проверяет, существует ли конечная трасса, удовлетворяющая
всем требованиям победивших норм. Таким образом, этот подход реализует алгоритм
проверки модели в ограниченном контексте, используя практическую решаемость
SMT-задач для конечных моделей [@bounded-model-checking; @barrett-smt-tutorial;
@smt-lib-2-7].

Существуют два основных варианта результата работы решателя:

1. **`sat`** — найдена нормативно корректная траса. В этом случае решатель
   представляет доказательство корректности: последовательность состояний, в
   которой значения `entity` удовлетворяют фактам и победившим правилам. Факт
   существования такой трассы можно интерпретировать как опровержение
   противоречивости набора норм, так как если она существует, данный набор
   нормативных положений на выбранном горизонте совместим.
2. **`unsat`** — нормативно корректной трассы на выбранном горизонте не найдено.
   В этом случае результат представляется как описание конфликта: несовместимые
   правила, участвующие факты, применённые приоритеты и связанные аннотации
   источников. Таким образом, пользователь получает не только значение `unsat`,
   но и объяснение, какие нормативные положения делают данный набор документов
   несовместимым.

### 3.1.3. Другие инструменты связанные с MDL

Инструментальная реализация MDL построена вокруг одного исполняемого файла
`mdl`. Пользовательские команды делятся на несколько групп.

- `parse` строит JSON-представление AST и используется для проверки синтаксиса,
  отладки генераторов и интеграции с внешними инструментами.
- `format` печатает канонический MDL-код и тем самым стабилизирует текстовое
  представление модели.
- `lint` выполняет статические проверки: разрешение имён, согласование типов,
  корректность деклараций и диагностирование ошибок до запуска решателя.
- `run` исполняет чистые термовые выражения и факты в поточечном runtime; эта
  команда нужна для проверки вспомогательных функций, но не заменяет
  темпорально-деонтический solve.
- `align` строит эвристические alignment-модули между несколькими MDL-моделями.
- `solve` выполняет проверку модели с помощью Z3.
- `lsp` запускает language server по stdio и позволяет использовать тот же
  парсер и статический анализ в редакторе [@microsoft-lsp-3-17].

Синтаксис языка задан грамматикой ANTLR, но кроме него, эквивалентная грамматика
так же определена в формате tree-sitter и text-mate. Таким образом, графический
редактор текста, LSP-сервер, инструмент форматирования, статический анализатор,
и CLI-команды опираются на один и тот же синтаксический источник истины. Если
модель создана автоматически, она всё равно проходит через общий pipeline:
лексер/парсер, AST, статический анализ, форматирование и только затем — проверка
решателем.

### 3.1.4. Python-подобный синтаксис MDL

MDL с ML-подобный синтаксисом в файлах `.mdl` является каноническим, однако
инструментальная реализация поддерживает второй входной формат — `.mdl.py`. Этот
язык является строгим подмножеством Python, с семантикой, полностью совместимой
с каноническим MDL. Таким образом, все инструменты и поведения вокруг MDL
остаются актуальными. По сути, `.mdl.py` имеет эквивалентное отображение в
`.mdl`

Модель записывается как обычный Python-файл с расширением `.mdl.py`, но
обрабатывается отдельным статическим компилятором. Компилятор разбирает исходный
код через Python AST, считывающим только эффективное для MDL подмножество:
импорт MDL модулей и открытие пространств имён, объявление модуля, записи с
аннотированными полями, объявления `entity`, чистые функции, предикаты, правила
и факты. Результатом обработки `.mdl.py` модуля является синтаксическое дерево,
эквивалентное каноническому MDL.

Минимальный пример `.mdl.py` выглядит следующим образом.

```{.python}
from mdl.dsl import *

module("standards.product")

@record
class Product:
  has_certificate: Bool
  mass_kg: Rat

product = entity(Product)

@predicate
def positive_mass(p: Product):
  return p.mass_kg > 0

@rule(O)
def certified_product():
  return always(product.has_certificate)

fact(product == Product(has_certificate=True, mass_kg=1500))
```

После компиляции и обработки анализатором такой исходный текст становится
эквивалентен каноническому MDL. `.mdl.py` является удобным входным синтаксисом
для разработчиков и алгоритмов генерации исходного кода, не знакомых с
семантикой и синтаксисом MDL, но результатом остаётся MDL-модель c сохранением
всех свойств.

```{.plain}
module standards.product

type Product = { has_certificate: bool, mass_kg: rat }

entity product: Product
func positive_mass(p: Product) -> bool:
  p.mass_kg > 0

rule O certified_product: product.has_certificate always

fact product = Product { has_certificate = true, mass_kg = 1500 }
```

Синтаксические соответствия между Python- и канонического синтаксиса взаимно
однозначно. `module("name")` задаёт модуль, `import_("...")` и `open_("...")`
соответствуют импортам и открытию пространств имён соответственно,
`@record class` задаёт тип-запись, `entity(T)` создаёт сущность, `@function` и
`@predicate` понижаются в чистые функции, `@rule(O)`, `@rule(P)` и `@rule(F)`
задают деонтические правила, а `fact(...)` добавляет ограничение контекста.
Темпоральные операторы реализованы в Python как функции `always(...)`,
`eventually(...)`, `next_(...)`, `now(...)` и `until(a, b)`.

Такой режим особенно полезен для автоматического вывода моделей из естественного
языка. Генератор может строить модель в более структурированной форме, чем
простая строковая генерация `.mdl`: сначала создать Python DSL-исходник, затем
скомпилировать его в AST, напечатать канонический MDL и уже после этого
запускать общий `lint` и `solve`. Это снижает число поверхностных синтаксических
ошибок, но не отменяет формальную проверку: любое заключение о противоречии всё
равно делается только решателем над зафиксированным MDL-контекстом.

Наряду с `mdl.dsl` остаётся низкоуровневый способ построения моделей напрямую в
Python: внешний процесс может создать `mdl.ast.Module` самостоятельно или
использовать `mdl.builder.ModelBuilder`. Такой API удобен, когда источник данных
уже является структурированным, например когда элементы модели приходят из
парсера, таблицы, онтологии или результата предварительного извлечения.
`ModelBuilder` добавляет в модуль импорты, открытия пространств имён, типы,
сущности, функции, правила и факты, а затем возвращает AST или печатает
канонический MDL-код через printer.

### 3.1.4. Интеграция модели с внешними инструментами

`fact` в MDL задаёт ограничение на проверяемую модель. В отличие от `rule`, факт
не является нормативным положением и не имеет имени. Факты фиксируют положение,
которое считается истинным на всём протяжении нормативной трассы.

Это свойство позволяет легко интегрировать внешние системы, такие как CAD или
SAP, без расширения ядра языка. Нормативный модуль описывает требования
стандарта, а отдельный контекстный модуль содержит факты, выгруженные из внешней
системы: материал, статус партии, наличие сертификата, значения измерений,
данные заказа или конфигурацию изделия. Тогда `solve` проверяет не только
совместимость норм между собой, но и совместимость конкретного состояния
проектируемого изделия с данным нормативным окружением.

```{.plain}
module context.autocad_snapshot_2026_06_14

import "../standards/product_requirements.mdl"
open standards.product_requirements

fact product.material = Material.Steel("09G2S")
fact product.has_certificate = true
fact product.mass_kg = 1500/1
```

Такой модуль может генерироваться автоматически расширением для внешней системы.
Внешняя система, не зная семантики MDL или деонтической структуры стандартов в
рамках которой разрабатывается изделие, передаёт только данные об этом изделии.
Таким образом разработчик изделия может получить информацию о соответствии
проектируемого изделия актуальному нормативному контексту, без анализа
нормативных документов непосредственно. При этом разработчику в любом случае
необходимо провести соответствие между разрабатываемым изделием и моделью
объекта стандартизации.

## 3.2. Вывод MDL из нормативных документов на естественном языке

В данном разделе рассмотрено обеспечение подсистемы вывода MDL-модулей из
текстов нормативных документов на естественном языке.

### 3.2.1. Утилита для генерации MDL моделей

Компонент `mdl-gen` выполняет синтез MDL из любого исходного документа. На вход
он получает текст, структуру документа, метаданные источника и, если доступно,
словари предметной области. На выходе он формирует один MDL-модуль. Минимальный
алгоритм работы `mdl-gen` задаётся следующими шагами.

1. **Сегментация документа.** Текст разбивается на нормативно значимые
   фрагменты: требования, определения, исключения, условия применимости, таблицы
   значений и ссылки на другие разделы.
2. **Выделение предметной модели.** Из фрагментов извлекаются устойчивые
   сущности, свойства, роли, единицы измерения и ограниченные варианты значений.
   На этом шаге формируются кандидаты в `type` и `entity`.
3. **Построение нормативных правил.** Для каждого требования определяется
   модальность (`O`, `F`, `P`), условие `when`, темпоральная форма тела правила
   и ссылка на источник.
4. **Выделение исключений и приоритетов.** Специальные случаи, оговорки и
   иерархии норм переводятся в `strict rule`, `defeater rule` и `override`.
5. **Статическая проверка.** Сгенерированный модуль форматируется, разбирается
   парсером, проходит `lint`, а затем проверяется на малых горизонтах для
   выявления грубых несоответствий.

MCP-контур нужен для того, чтобы генератор мог обращаться к инструментам MDL как
к внешним операциям: получить выдержку из спецификации языка, построить AST,
запустить форматирование, получить диагностические сообщения от статического
анализатора, выполнить `solve` на тестовом горизонте и вернуть замечания в цикл
исправления. Тем самым языковая модель используется не как единственный источник
истины, а как компонент синтеза, ограниченный грамматикой, системой типов и
решателем MDL.

На уровне реализации возможны два режима вывода. В текстовом режиме `mdl-gen`
порождает `.mdl` исходный код и затем исправляет его по диагностике. В
структурном режиме он строит `mdl.ast.Module` или использует
`mdl.builder.ModelBuilder`, после чего печатает канонический MDL-код. Второй
режим предпочтителен для стабильных пайплайнов, потому что часть ошибок
синтаксиса устраняется ещё до печати текста.

### 3.2.2. Эксперимент по обратной связи

Для выбора режима обратной связи в контуре `mdl-gen` был проведён расширенный
эксперимент по влиянию инструкций и семантической обратной связи на качество
межмодельного выравнивания. Эксперимент не оценивал истинность сгенерированной
модели относительно исходного RFC и не проверял наличие противоречий в самих
документах. Измерялась более узкая, но важная для последующего MDL-контура
характеристика: насколько независимо сгенерированные формальные модели одного и
того же документа сопоставимы между собой по типам, свойствам, отношениям и
другим элементам схемы.

В качестве промежуточного языка эксперимента использовались C#-модели. В этом
контексте C# рассматривался не как исполнимая реализация, а как строго
структурированное представление предметной модели: классы, перечисления,
свойства и связи извлекались из кода как элементы схемы. Такой эксперимент
проверяет не конечную семантику MDL, а один из ключевых рисков автоматического
вывода моделей из естественного языка — нестабильность имён и структуры при
независимой генерации.

Корпус включал 32 RFC нормативного характера по четырём группам тем: HTTP, URI и
поведение веб-протоколов; JSON и форматы данных; OAuth, токены и аутентификация;
операционная безопасность и политики доступа. В корпусе было 30 714 строк и 156
985 слов. Для каждого документа использовались шесть генеративных моделей, три
сценария генерации и пять независимых запусков, что дало полный набор из

$$
32 \cdot 6 \cdot 3 \cdot 5 = 2880
$$

итоговых C#-артефактов.

Сравнивались три сценария генерации.

| Сценарий   | Содержание                                                                                                                                                                                          |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `control`  | Генерация C#-доменной модели из исходного документа без дополнительных инструкций.                                                                                                                  |
| `guided`   | Генерация по единой инструкции, задающей правила именования, структурирования и представления элементов модели.                                                                                     |
| `feedback` | Сначала выполняется `guided`-генерация; затем более крупная модель анализирует результат на нарушения инструкции и формирует замечания; после этого исходная генеративная модель ревизует артефакт. |

После генерации из каждого C#-артефакта извлекались элементы четырёх типов:
`enum member`, `property`, `relation` и `type`. Для выравнивания строились три
слоя проекции: свойства по путям, типы по составу членов и отношения по путям с
метаданными. Артефакты группировались по исходному документу, сценарию и номеру
запуска; разные сценарии напрямую друг с другом не выравнивались. Внутри каждой
группы строились направленные пары между результатами разных генеративных
моделей. При шести моделях это даёт $6\cdot5=30$ направленных пар на группу и 14
400 пар по всему эксперименту.

Выравнивание выполнялось двумя COMA-подобными реализациями: `valentine:coma_py`
и `bdikit:coma` [@do2002coma; @aumueller-coma-2005; @koutras-valentine-2021;
@lopez2026bdikit]. С учётом трёх слоёв проекции было выполнено 86 400 операций
выравнивания, из которых 71 523 дали непустые срезы. Кандидаты сопоставления
внутри одной пары не считались независимыми наблюдениями; сравнение сценариев
выполнялось по агрегированным срезам и дополнительно проверялось попарно на
уровне документов.

Основная метрика эксперимента, `pair_alignment_f1`, вычислялась как произведение
`coverage_f1` и `top1_mean_score`. Первая компонента показывает, какая доля
элементов обеих моделей вообще вовлечена в найденные соответствия. Вторая
компонента показывает среднюю оценку лучшего кандидата для сопоставляемых
элементов. Поэтому `pair_alignment_f1` отражает одновременно покрытие структуры
и уверенность алгоритма выравнивания. Эта метрика не доказывает правильность
соответствий относительно эталонной разметки, но позволяет сравнивать, насколько
разные сценарии генерации подготавливают модели к автоматическому сопоставлению.

Результаты показали, что оба структурированных сценария существенно лучше
контрольного, однако обратная связь не превзошла сценарий с инструкциями.

| Сравнение            | $\Delta$ `coverage_f1` | $\Delta$ `pair_alignment_f1` | Относительное изменение `pair_alignment_f1` |
| -------------------- | ---------------------: | ---------------------------: | ------------------------------------------: |
| `guided - control`   |                +0,0766 |                      +0,1517 |                                      +46,2% |
| `feedback - control` |                +0,0738 |                      +0,1323 |                                      +40,3% |
| `feedback - guided`  |                -0,0028 |                      -0,0193 |                                       -4,0% |

На уровне документов `guided` и `feedback` превосходили `control` во всех 32
RFC. При этом `feedback` оказался лучше `guided` только в 9 документах из 32.
Направление эффекта сохранялось для обеих реализаций выравнивания: разность
`feedback - guided` составила -0,0213 для `bdikit:coma` и -0,0174 для
`valentine:coma_py`. Следовательно, вывод не является артефактом одного
конкретного matcher'а.

Разложение метрики показывает механизм результата. У `guided` и `feedback` почти
совпадает покрытие: `coverage_f1` равно 0,6140 и 0,6111 соответственно. Главное
различие связано с `top1_mean_score`: 0,7657 у `guided` против 0,7406 у
`feedback`. Значит, обратная связь не разрушает возможность вовлечь элементы в
сопоставление, но снижает среднюю уверенность алгоритма в лучшем кандидате.
Практически это объясняется тем, что ревизия по замечаниям может делать имена
более предметными и подробными для человека, но одновременно увеличивать
разнообразие формулировок между разными генеративными моделями.

Для `mdl-gen` из этого следует инженерное ограничение. Наиболее надёжным базовым
режимом является не произвольная итеративная обратная связь, а заранее заданная
инструкция о структуре модели, семантике имён, единицах измерения, ролях и
связях. Обратная связь полезна как механизм исправления ошибок, но её нужно
оптимизировать не только на локальную выразительность модели, но и на
каноничность, межмодельную сопоставимость и устойчивость последующего
alignment-этапа. Иначе дополнительная ревизия может улучшить видимость
семантической проработки, но ухудшить качество автоматического сопоставления.

## 3.3. Индекс отношений

При анализе большого корпуса документов недостаточно запускать `solve` только на
одном явно выбранном модуле. Противоречие часто возникает не внутри отдельного
нормативного документа, а между требованиями разных документов, которые говорят
об одном объекте. Поэтому системе нужен индекс отношений между элементами
MDL-моделей.

Индекс отношений хранит связи между свойствами `entity`, типами, полями и
правилами. На минимальном уровне запись индекса содержит:

- исходный модуль, `entity` и путь к свойству;
- целевой модуль, `entity` и путь к свойству;
- тип связи: эквивалентность, уточнение, обобщение, преобразование единицы
  измерения, зависимость или потенциальный конфликт;
- оценку уверенности и источник связи: matcher, эксперт, импортированный
  словарь, предыдущее решение системы;
- статус: кандидатная, принятая, отклонённая или требующая экспертной проверки.

Например, индекс может хранить связь между `pipe.outer_diameter_mm` в одном
модуле и `tube.diameter_mm` в другом, а также связь между
`product.material.grade` и `material_certificate.steel_grade`. Сами по себе эти
связи не доказывают противоречие. Они только показывают, какие модули и
alignment-правила имеют смысл добавить в общий контекст проверки.

При запуске `solve` система анализирует множество `entity` и свойств,
используемых в выбранных модулях, обращается к индексу отношений и предлагает
дополнительный контекст: модули со связанными требованиями, ранее принятые
alignment-модули, словари единиц измерения и внешние факты. После выбора или
автоматического принятия такого контекста формальная проверка выполняется тем же
решателем Z3. Таким образом индекс решает задачу поиска релевантного контекста,
но не заменяет логическую проверку.

В терминах архитектуры индекс отношений является специальной базой данных вокруг
MDL, а не частью синтаксиса языка. Это важно для воспроизводимости: один и тот
же набор модулей и alignment-правил должен давать один и тот же результат
`solve` независимо от того, каким способом эти модули были найдены. Индекс
ускоряет и направляет поиск, но утверждение о противоречии остаётся свойством
явно зафиксированного контекста проверки.

## 3.4. Оценка качества MDL

Качество MDL как промежуточного представления оценивается не только по
синтаксической корректности моделей, но и по способности всей цепочки находить
противоречия в размеченных корпусах. Поэтому целевая оценка должна включать как
инженерные метрики, так и метрики обнаружения противоречий.

К инженерным метрикам относятся доля моделей, успешно разобранных парсером,
число ошибок `lint`, успешность запуска `solve`, доля правил с аннотациями
источника, доля устойчиво названных `entity` и воспроизводимость результата при
повторной генерации. Эти метрики показывают, пригодна ли модель для
автоматической обработки. Однако основная прикладная метрика — доля найденных
противоречий на корпусе, где есть независимая разметка или экспертно
подтверждённый список конфликтов.

Для корпуса с множеством размеченных противоречий $C$ и множеством противоречий,
найденных системой, $D$, полнота поиска задаётся как

$$
\text{recall} = \frac{|C \cap D|}{|C|}.
$$

Дополнительно должна измеряться точность

$$
\text{precision} = \frac{|C \cap D|}{|D|},
$$

поскольку система, которая объявляет противоречивыми слишком много пар
требований, непригодна для экспертной работы даже при высокой полноте.

### 3.4.1. Доля найденных противоречий на Contract-NLI

Первый оценочный контур планируется построить на датасете Contract-NLI. Его
задача — проверить, какую долю текстовых противоречий между договорными
положениями удаётся восстановить после перевода в MDL и запуска `solve`.
Поскольку Contract-NLI размечен в терминах отношений между фрагментами текста,
необходимо выделить подмножество примеров, которые действительно переводятся в
форму typed entities, facts и deontic/temporal rules.

Схема оценки должна включать четыре шага: перевод пары фрагментов в MDL,
статическую проверку модели, запуск `solve` на фиксированном горизонте и
сравнение результата с исходной NLI-разметкой. Положительным срабатыванием
считается случай, когда пример с меткой contradiction после формализации даёт
`unsat` или объяснимый конфликт правил. Для примеров entailment и neutral
система не должна возвращать противоречие.

В текущей редакции это заглушка эксперимента. Итоговые значения полноты,
точности и ошибки формализации должны быть добавлены после подготовки
согласованного MDL-представления выбранной части Contract-NLI.

### 3.4.2. Качество обнаружения противоречий в RFC

Второй оценочный контур связан с RFC-документами. RFC удобны как промежуточный
корпус: они технически точны, содержат нормативные формулировки, часто
используют модальные слова вроде MUST, SHOULD и MAY, но при этом остаются
документами на естественном языке. Для MDL это позволяет проверить не только
правильность логического solve, но и качество извлечения сущностей, условий,
исключений и временных зависимостей.

План оценки включает построение MDL-модулей для группы связанных RFC,
выравнивание сущностей и свойств через индекс отношений, запуск `solve` на
подобранных контекстах и экспертную проверку найденных конфликтов. Отдельно
следует учитывать известные errata, обновления RFC и случаи, когда кажущееся
противоречие снимается разными версиями документа или разными областями
применения.

Метриками этого контура должны стать число найденных экспертно подтверждённых
противоречий, `precision@k` для ранжированного списка конфликтов, доля
ложноположительных результатов из-за ошибочного выравнивания и доля конфликтов,
которые устраняются после добавления недостающего контекста из индекса
отношений.

### 3.4.3. Качество обнаружения противоречий на корпусе ГОСТ из Техэксперта от АО «Кодекс»

Третий оценочный контур относится к корпусу ГОСТ, полученному из СПС
«Техэксперт» от АО «Кодекс». Этот корпус ближе к целевому сценарию применения,
поскольку содержит отечественные нормативные документы, связанные между собой
терминами, ссылками, объектами стандартизации, редакциями и областью применения.
Для такой проверки особенно важны трассируемость к пунктам документа,
нормализация терминологии и корректная работа индекса отношений.

Эксперимент должен оценивать три аспекта. Первый аспект — способность `mdl-gen`
построить корректные MDL-модули по фрагментам ГОСТ. Второй аспект — качество
индекса отношений: насколько хорошо он предлагает дополнительные модули и
alignment-правила при запуске `solve`. Третий аспект — качество обнаружения
противоречий: доля экспертно подтверждённых конфликтов, доля ложных срабатываний
и трудоёмкость экспертной валидации одного найденного конфликта.

Для практической применимости важно также проверять сценарий с внешними фактами:
например, когда данные о конкретном изделии или партии поступают из SAP, а
требования берутся из ГОСТ. В этом случае система должна объяснять, противоречит
ли конкретная конфигурация нормативному окружению, или же противоречие
существует уже между самими нормативными модулями.

В текущей редакции раздел является заделом под промышленную оценку. Численные
результаты должны быть внесены после формирования корпуса, экспертной разметки и
согласования правил доступа к исходным документам.

## 3.5. Выводы по главе

В главе описан инженерный слой системы обнаружения противоречий. MDL задаёт язык
промежуточного представления требований: типы и `entity` фиксируют предметную
область, `rule` выражает деонтические и темпоральные нормы, `fact` подключает
внешний контекст, а `override`, `strict rule` и `defeater rule` задают
исключения и приоритеты. Решатель на основе Z3 проверяет набор модулей на
конечном горизонте и возвращает либо witness trace для `sat`, либо объяснимый
конфликт для `unsat`.

Также зафиксированы три направления развития инструментального контура:
автоматический вывод MDL из естественного языка через `mdl-gen` и MCP,
индексация отношений между свойствами `entity` для подбора контекста при
`solve`, а также оценка качества MDL на Contract-NLI, RFC и корпусе ГОСТ из
«Техэксперта» АО «Кодекс». Эти компоненты отделяют эвристические этапы поиска и
подготовки моделей от формального вывода о противоречии, который остаётся
задачей решателя над явно заданным MDL-контекстом.
