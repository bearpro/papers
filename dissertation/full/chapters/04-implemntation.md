# 3. Методы реализации системы: MDL, выравнивание и индекс отношений

Глава раскрывает третий научный результат работы. Формализм DDL-LTLf задаёт математическую семантику противоречия, но прикладной системе нужен ещё один слой: язык для записи требований, инструменты построения моделей, механизмы выравнивания моделей из разных источников и способ отбирать пары требований для последующей формальной проверки.

## 3.1. Контур реализации системы

В прикладном контуре исходные документы сначала переводятся в формальные модели, затем модели приводятся к сопоставимому виду, после чего проверяемый набор норм передаётся в решатель. Этот контур включает пять связанных этапов.

1. Синтез промежуточного представления из исходного документа: из SMART-документа, структурированного формата или естественно-языкового текста строится MDL-модель.
2. Статическая проверка и канонизация: парсер, linter, type checker и formatter отбраковывают синтаксические ошибки, неоднозначные имена и несогласованные типы.
3. Межмодельное выравнивание: для разных MDL-модулей строятся соответствия между типами, сущностями, свойствами и отношениями.
4. Индексация отношений моделей: найденные соответствия и связанные с ними элементы требований сохраняются в индексе, чтобы система не выполняла полный попарный перебор документов при каждом запросе.
5. Формальная проверка: MDL-модули и принятые alignment-модули транслируются в DDL-LTLf core JSON и проверяются решателем на конечном горизонте.

Такой контур задаёт двухконтурную схему поиска. Вероятностные и эвристические методы используются для генерации модели, канонизации и отбора кандидатов, а само утверждение о противоречии проверяется формальной процедурой на основе DDL-LTLf и SAT-сведения. MDL в этой схеме является доменно-специфичным языком [@fowler2010dsl]: он не заменяет универсальный язык программирования, а фиксирует те конструкции, которые нужны для нормативной семантики, трассируемости и проверки согласованности.

## 3.2. Семантическая структура MDL

Срез реализации от 8 июня 2026 года описывает MDL как ML-подобный язык для нормативных моделей [@prokazin-mdl]. Его инструментальная цепочка имеет следующий вид:

```{.plain}
.mdl source
  -> lexer/parser
  -> AST
  -> format/lint/run/translate/solve
  -> DDL-LTLf core JSON
  -> finite-trace solver
```

Инструменты работают в разных режимах. `run` исполняет обычные выражения, функции, факты, pattern matching и часть стандартной библиотеки как поточечный runtime. Он не интерпретирует темпоральную и деонтическую семантику. Для проверки норм используются `translate` и `solve`: первый строит независимое от backend представление DDL-LTLf core JSON, второй кодирует правила и темпоральные формулы на конечном горизонте.

Модель требований MDL имеет три уровня: термовый, темпоральный и деонтический.

На термовом уровне описываются данные, значения и чистые вычисления. Этот уровень задаёт предметную область без нормативной интерпретации.

```{.plain}
type Pipe = { length: rat, radius: rat }

func has_positive_geometry(p: Pipe) -> bool:
  p.length > 0 and p.radius > 0
```

Функция `has_positive_geometry` задаёт булев предикат над объектом. Для включения в темпоральные и деонтические конструкции используются выражения типа `bool`, соответствующие атомарным пропозициям формализма DDL-LTLf. Термовый уровень не содержит ввода-вывода, mutable assignment и циклов; вычисления остаются чистыми.

На темпоральном уровне булевы выражения связываются операторами LTLf на конечных трассах. Поддерживаются `always`, `eventually`, `next`, `initially`, `until` и специальное имя `last`, истинное только на последнем шаге трассы [@degiacomo2013ltlf].

```{.plain}
has_positive_geometry(pipe) always
```

На деонтическом уровне определяются `entity`, `fact`, правила и приоритеты. Правила используют модальности обязанности, запрета и разрешения.

```{.plain}
entity invoice_issued: bool
entity paid: bool
entity closed: bool

fact invoice_issued = true

rule O pay_when_due when invoice_issued: paid eventually
rule F no_unpaid_closure when invoice_issued: closed and not paid
```

Дефизибельность выражается через условия применимости, `strict`-правила, `defeater`-правила и `override`.

```{.plain}
rule O perform_work when scheduled: work_done eventually

strict rule F unsafe_mode: system_unsafe always

defeater rule F maintenance_exception when maintenance: work_done always

override maintenance_exception > perform_work
```

`when` задаёт применимость нормы, `strict` фиксирует непоражаемое правило, `defeater` блокирует нижестоящее правило без собственного требования, а `override` задаёт отношение приоритета. Разрешение `P` параметризуется на уровне solver option: в режиме `strong` оно добавляет требование, в режиме `ignore` не добавляет [@governatori2013permissions; @governatori2018practical].

## 3.3. Типы, модули, факты и трассируемость

Синтаксис MDL использует решения языков семейства ML: статическую типизацию, алгебраические типы данных, параметрические типы, записи, кортежи, pattern matching и чистые функции [@milner1978polymorphism; @milner1997sml]. В актуальной реализации определены примитивные типы `bool`, `int`, `rat`, `decimal`, `string` и `unit`. Литерал `()` имеет тип `unit`; он нужен, в частности, для нульарных конструкторов алгебраических типов.

```{.plain}
type Pipe = { length: rat, radius: rat }
type Option<T> = None(unit) | Some(T)
type Result<T, E> = Ok(T) | Err(E)
```

Каждый `.mdl` файл является модулем. Файл начинается с обязательной декларации `module`, после которой могут идти `import`, `open` и верхнеуровневые декларации.

```{.plain}
module standards.pipe

import "std/collections.mdl"
open std.collections

type Pipe = { length: rat, radius: rat }
entity pipe: Pipe
```

`import` принимает строковый путь к файлу, а `open` вносит экспортируемые имена модуля в короткую область видимости. Это важно для повторного использования словарей, коллекций, типов предметной области и моделей документов. Верхнеуровневые декларации включают `type`, `let`, `func`, `entity`, `fact`, `rule` и `override`. `entity` задаёт именованную переменную состояния или трассы для решателя, а `fact` фиксирует значение или булево условие.

Трассируемость задаётся аннотациями у модуля и верхнеуровневых конструкций. Аннотация начинается с `@` и сохраняется в AST и core-представлении.

```{.plain}
@source: RFC 2822
module email

@source: RFC 2822 section 3.4.1
rule O email_addr_spec_correct: email_is_correct(email) always
```

Результат работы решателя должен возвращать не только статус `sat` или `unsat`, но и объяснение: нормативно корректную трассу для непротиворечивого набора требований либо набор несовместимых правил с аннотациями источников для противоречивого набора. Поэтому трассируемость является частью интерпретации результата поиска противоречий [@gotel1994traceability; @alkhammash2015traceable-eventb].

## 3.4. Инструментальная цепочка и функциональная проверка

Инструментальная реализация MDL включает parser, formatter, semantic checker/linter, type inference, поточечный runtime, core translator, решатель на конечном горизонте, aligner и LSP-сервер. Для пользователя это выражается в командах `parse`, `format`, `lint`, `translate`, `run`, `solve`, `align` и `lsp`.

`translate` строит DDL-LTLf core JSON. В core сохраняются module, annotations, imports/opens, types, values, entities, rules, priorities, facts и lifted atoms. Булевы и темпоральные конструкции отображаются на `not`, `and`, `or`, `implies`, `G`, `F`, `X`, `U`, `initially` и `last`. Вызовы функций, возвращающие `bool`, могут подниматься в атомы с нормализованными именами; тело произвольной функции не компилируется в core как универсальная программа.

`solve` проверяет один или несколько модулей на фиксированном горизонте либо перебирает горизонты до `max_horizon`. Он создаёт переменные для `entity` на каждом шаге трассы, учитывает `fact`, применимость правил, defeat relation и требования победивших норм. Для `override r1 > r2 > r3` текущая реализация строит соседние пары поражения; если нужна прямая пара `r1 > r3`, её нужно задать явно.

Функциональная проверка реализации выполнялась на наборе из 82 модульных тестов и 14 полных сценариев с заранее подготовленными моделями [@prokazin-mdl]. В сценарии `polyeq_rat` модель задаёт полиномиальное уравнение как набор нормативных требований, а решатель подтверждает существование нормативно корректной трассы со статусом `sat`. При изменении правила так, что коэффициенты делают уравнение неразрешимым, решатель возвращает `unsat` и перечисляет несовместимые правила.

## 3.5. Канонизация, выравнивание и индекс отношений моделей

После синтеза MDL-моделей система должна привести их к сопоставимому виду. Канонизация стабилизирует имена сущностей, типов, полей, единиц измерения и ролей. Статический анализ не решает задачу семантической эквивалентности полностью, но уменьшает число поверхностных расхождений, из-за которых алгоритм выравнивания видит разные элементы там, где эксперт видит один и тот же объект.

Выравнивание выполняется инструментом `mdl align`. Он принимает два или более MDL-модуля, matcher, пороги кандидатов и принятия, а затем формирует отчёт и обычный MDL-модуль с выравнивающими правилами. Сам `align` не является грамматической конструкцией языка; это часть инструментальной цепочки.

```{.plain}
module alignment.pipe_tube

import "./pipe.mdl"
import "./tube.mdl"

@align: kind=field score=0.800 matcher=bdikit:coma
rule O alignment_001: pipe.pipe.length == tube.tube.length always
```

Такой alignment-модуль становится частью входа решателя. Если найденное противоречие зависит от результата выравнивания, эксперт видит конкретное выравнивающее правило в цепочке причин и может удалить или уточнить его средствами MDL. В текущей инструментальной цепочке для построения соответствий используются COMA-подобные алгоритмы [@do2002coma; @lopez2026bdikit; @aumueller-coma-2005].

Индекс отношений моделей хранит принятые и кандидатные связи между элементами: исходный модуль, целевой модуль, тип связи, score, matcher, источник и статус экспертной проверки. Такой индекс нужен по двум причинам. Во-первых, он исключает полный перебор всех пар документов при каждом новом анализе. Во-вторых, он отделяет вероятностный этап отбора кандидатов от формальной проверки: solver получает только те связи, которые прошли порог, были приняты экспертом или выведены из уже принятых связей.

## 3.6. Проблема сопоставимости формальных моделей

Даже если каждая отдельная модель синтаксически корректна, это не гарантирует её сопоставимость с другими моделями. При независимом переводе одного и того же документа в формальный язык разные авторы или разные генеративные модели могут выбирать разные имена для одних и тех же сущностей, использовать разные уровни детализации, по-разному выражать роли, состояния, единицы измерения и связи.

При анализе больших массивов документов ручное попарное сопоставление невозможно. Требуется массовое межмодельное выравнивание: автоматическое нахождение соответствий между типами, свойствами, отношениями и другими элементами моделей [@rahm-bernstein-schema-matching-2001; @shvaiko-euzenat-ontology-matching-2013]. Стандарты обмена требованиями, например ReqIF, решают задачу переноса артефактов между инструментами, но не устраняют проблему семантической несогласованности моделей [@omg-reqif-1-2; @teremov-prokazin-rusreqif].

Семантическая обратная связь рассматривается как один из способов подготовки моделей к выравниванию. До этапа сопоставления она должна стабилизировать имена типов, полей, ролей, единиц измерения и состояний. Такой анализ может быть реализован как языковой сервер или LSP-подобный слой диагностик [@microsoft-lsp-3-17]. В эксперименте промышленный LSP-сервер не реализовывался: использовалась процедура, имитирующая семантические предупреждения для генеративной модели.

## 3.7. Постановка расширенного эксперимента

В расширенном эксперименте исследуется влияние сценариев генерации на качество межмодельного выравнивания C#-моделей технических спецификаций. C# используется не как целевая платформа исполнения, а как структурированное промежуточное представление: типы, свойства, перечисления и отношения извлекаются из кода как элементы схемы [@ecma-csharp-334-2023].

Исследовательские вопросы формулируются следующим образом.

1. Улучшает ли инструкция по структурированию и семантическому именованию межмодельную выравниваемость относительно генерации без дополнительных инструкций?
2. Улучшает ли обратная связь межмодельную выравниваемость относительно сценария с инструкциями?
3. Насколько устойчивы наблюдаемые эффекты по документам, алгоритмам выравнивания, слоям проекции и генеративным моделям?

Корпус включает 32 RFC-документа нормативного характера. Документы сгруппированы по четырём темам: HTTP, URI и поведение веб-протоколов; JSON и форматы данных; OAuth, токены и аутентификация; операционная безопасность и политики доступа [@rfc2026]. Общий объём корпуса составляет 30 714 строк и 156 985 слов, среднее число слов на документ - 4 905,8.

В эксперимент включены шесть генеративных моделей:

- `anthropic/claude-haiku-4.5`;
- `deepseek/deepseek-chat-v3.1`;
- `google/gemini-2.5-flash`;
- `mistralai/mistral-medium-3.1`;
- `openai/gpt-5-mini`;
- `qwen/qwen3-235b-a22b`.

Для каждой комбинации документа, модели и сценария выполнялось пять независимых запусков. Рассматривались три сценария:

| Сценарий | Описание |
|---|---|
| `control` | Генерация C#-доменной модели из исходного документа без дополнительных инструкций. |
| `guided` | Генерация с инструкциями, задающими правила именования, структурирования и представления элементов модели. |
| `feedback` | Сначала выполняется `guided`-генерация; затем более крупная модель `openai/gpt-5` анализирует C#-файл на предмет нарушения инструкций и генерирует обратную связь; после этого исходная модель выполняет ревизию. |

Матрица эксперимента:

$$
D = 32, \quad M = 6, \quad S = 3, \quad R = 5.
$$

Число полученных финальных артефактов:

$$
D \cdot M \cdot S \cdot R = 32 \cdot 6 \cdot 3 \cdot 5 = 2880.
$$

Для каждой группы, заданной документом, сценарием и номером запуска, строились направленные пары между результатами разных генеративных моделей. При шести моделях это даёт $M(M-1)=30$ направленных пар на группу, всего:

$$
N_{\text{pairs}} = 32 \cdot 3 \cdot 5 \cdot 6 \cdot 5 = 14400.
$$

Выравнивание выполнялось по трём слоям проекции (`property`, `type`, `relation`) и двум COMA-подобным алгоритмам: `valentine:coma_py` и `bdikit:coma` [@koutras-valentine-2021; @lopez-bdikit-demo-2026]. Запланированный объём составляет:

$$
N_{\text{ops}} = 14400 \cdot 3 \cdot 2 = 86400
$$

операций выравнивания. Из них получено 71 523 непустых среза.

## 3.8. Метрики и полнота данных

Основные метрики эксперимента:

- `source_coverage`: доля элементов исходной модели, участвующих хотя бы в одном кандидате;
- `target_coverage`: доля элементов целевой модели, участвующих хотя бы в одном кандидате;
- `coverage_f1`: гармоническое среднее между `source_coverage` и `target_coverage`;
- `top1_mean_score`: средняя оценка лучшего кандидата для исходных элементов с непустым набором кандидатов;
- `pair_alignment_f1`: основная метрика, равная произведению `coverage_f1` и `top1_mean_score`.

$$
\operatorname{coverage\_f1} =
\frac{2 \cdot \operatorname{source\_coverage} \cdot \operatorname{target\_coverage}}
{\operatorname{source\_coverage} + \operatorname{target\_coverage}}.
$$

$$
\operatorname{pair\_alignment\_f1} =
\operatorname{coverage\_f1} \cdot \operatorname{top1\_mean\_score}.
$$

Метрика `pair_alignment_f1` объединяет два аспекта: насколько большая часть структуры вовлекается в выравнивание и насколько уверенно matcher оценивает лучшие соответствия. Она не заменяет экспертную разметку истинности соответствий, но позволяет сравнить относительную пригодность разных сценариев генерации для автоматического выравнивания.

Эксперимент выполнен на полном запланированном объёме: 2 880 моделей, 8 640 проекций, 115 614 выделенных элементов схем, 14 400 направленных пар и 86 400 операций выравнивания.

| Группа артефактов | Количество |
|---|---:|
| Сгенерировано моделей | 2 880 / 2 880 |
| Выполнено проекций | 2 880 × 3 |
| Выделено элементов моделей | 115 614 |
| Построено направленных пар | 14 400 |
| Выполнено операций выравнивания | 86 400 |
| Сопоставлено элементов | 648 269 |
| Оценено попарных срезов | 71 523 |

## 3.9. Результаты расширенного эксперимента

Ошибки в грамматике исходного кода были редкими: медиана числа ошибок равна нулю во всех сценариях. При этом суммарное число parse errors возрастает от `control` к `guided` и `feedback`: 51, 118 и 247 соответственно.

| Сценарий | Артефактов | Суммарное число ошибок | Среднее число ошибок | Максимум | Доля без ошибок |
|---|---:|---:|---:|---:|---:|
| `control` | 960 | 51 | 0,053 | 7 | 97,7% |
| `guided` | 960 | 118 | 0,123 | 50 | 99,1% |
| `feedback` | 960 | 247 | 0,257 | 64 | 98,4% |

Всего из 2 880 C#-артефактов было извлечено 115 614 элементов схем. Сценарий `control` дал больше элементов, чем `guided` и `feedback`, поэтому улучшение выравниваемости структурированных сценариев не объясняется простым ростом числа элементов.

|---|---:|---:|---:|---:|---:|
| `control` | 6 125 | 25 319 | 4 165 | 8 598 | 44 207 |
| `guided` | 3 655 | 21 686 | 3 618 | 6 677 | 35 636 |
| `feedback` | 3 658 | 21 668 | 3 644 | 6 801 | 35 771 |

Средние оценки по всем документам, парам генеративных моделей, запускам, слоям проекции и методам выравнивания показывают устойчивое преимущество `guided` и `feedback` над `control`. Однако `feedback` не превосходит `guided` по основной метрике.

![Основные метрики по сценариям](./assets/fig-overall-alignment-metrics.png){#fig:overall-alignment-metrics width=95%}

| Сравнение | Coverage F1 delta | Pair alignment F1 delta | Relative pair-alignment change |
|---|---:|---:|---:|
| `guided - control` | +0,0766 | +0,1517 | +46,2% |
| `feedback - control` | +0,0738 | +0,1323 | +40,3% |

По основной метрике лучший сценарий для массового выравнивания COMA-подобными алгоритмами - `guided`. `feedback` сохраняет большую часть выигрыша относительно `control`, но не улучшает результат сценария с инструкциями.

Механизм результата виден из разложения метрики. У `guided` и `feedback` близкие значения `coverage_f1`: 0,6140 и 0,6111. Основное различие связано с `top1_mean_score`: 0,7657 у `guided` против 0,7406 у `feedback`. Следовательно, обратная связь не столько разрушает покрытие, сколько снижает среднюю уверенность алгоритма сопоставления в лучших кандидатах.

Попарное сравнение на уровне документов подтверждает устойчивость улучшения относительно `control`. И `guided`, и `feedback` превосходят `control` во всех 32 документах, но `feedback` превосходит `guided` только в 9 из 32 документов.

![Средние разности при попарном сравнении на уровне документов](./assets/fig-document-deltas-ci.png){#fig:document-deltas-ci width=95%}

## 3.10. Выводы по главе

По главе получены три результата.

Первый результат - язык MDL как инженерный слой между текстом нормативного документа, формальной семантикой DDL-LTLf и решателем противоречий. Для диссертационной задачи нужны не только деонтические и временные операторы, но и модульность, типизация, `entity`/`fact`, трассируемость, core JSON, статический анализ, `align` и LSP-контур диагностики.

Второй результат - схема подготовки моделей к проверке: канонизация имён, межмодельное выравнивание и индекс отношений моделей. Эта схема отделяет вероятностный отбор кандидатов от формального вывода о противоречии.

Третий результат - экспериментальная оценка сценариев генерации. На 32 RFC-документах, шести генеративных моделях и 2 880 артефактах структурированные инструкции повышают `pair_alignment_f1` относительно контроля на 46,2%, а сценарий с обратной связью - на 40,3%. При этом `feedback` не превосходит `guided`: разность `feedback - guided` составляет -0,0193, или -4,0%. Для массового выравнивания моделей COMA-подобными алгоритмами полезнее сразу задавать единые правила структурирования и семантического именования, чем выполнять дополнительную ревизию по обратной связи.
